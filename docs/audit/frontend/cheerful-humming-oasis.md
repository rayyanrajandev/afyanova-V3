# AfyaNova V3 — Frontend Remediation Plan

## Context

A frontend audit (same rigor as the original backend audit: a full route-to-UI cross-reference of all 120 named Laravel routes against every `route()` call in the Vue codebase, security-pattern scanning, and a manual read of every security-critical component) found that the backend gap-closure work already shipped — tenancy/RLS depth, AES-256-GCM PII encryption, real TOTP MFA, break-glass, full audit-trail coverage, and 8 new clinical/financial modules (consent, referral, immunization, ANC, partograph, problem list, medication reconciliation, radiology) — landed with **zero frontend UI for any of the 8 new modules**, plus a handful of pre-existing frontend gaps the cross-reference surfaced along the way.

The frontend itself (94 Vue files, ~19,000 lines, Inertia.js + Vue 3, no TypeScript) is a real, substantial, mostly well-built application — not a prototype. But three things are true at once: (1) every one of the 8 new backend modules is unreachable from the browser, (2) the route cross-reference surfaced several older orphaned routes and one previously-unknown backend bug (a controller method that doesn't exist — would 500 if ever hit), and (3) while grounding this plan against the actual code, a foundational bug was found that the audit itself missed — **Inertia's shared `flash` prop is never actually shared**, so every controller's `back()->with('success', ...)` / `->withErrors(...)` flash message has been silently invisible to users since `AfyaShell.vue`'s global banner was written (it reads `page.props.flash?.success`, which has never existed in `page.props` at all — confirmed by reading `app/Http/Middleware/HandleInertiaRequests.php::share()` directly, which returns only `auth` and `ziggy`). `BreakGlassController::store()` additionally flashes under the literal key `'flash.success'` instead of `'success'` — a typo that would still break even after the middleware fix.

This plan closes every finding, in dependency order: cheap/foundational fixes first, then the backend relations the new UI needs, then the UI itself (encounter-scoped tabs → patient-scoped tabs → the one genuinely new page), then the remaining smaller orphaned-route gaps, then test/tooling infrastructure, then accessibility.

Per your direction: `access-control.facilities.assign` (the route pointing at a nonexistent controller method) is treated as dead scaffolding to delete, not a feature to build — role assignment's existing `facility_id` field is already the app's one facility-scoping mechanism, and there's no other trace of a standalone facility-only assignment concept anywhere in the Identity domain's models.

## Phase F0 — Foundational fixes (do first; each item is small and independent)

- **Git init.** This repo has never been placed under version control — confirmed at the start of the engagement, and confirmed again by the discovery that `.github/workflows/ci.yml` (a well-built pipeline that runs Pest against a real Postgres service container, per its `DB_CONNECTION: pgsql` step env and `phpunit.xml` not forcing SQLite over an externally-set env var) has never once executed, because there's no commit to trigger it. `git init`, stage everything, one initial commit — before any other change in this plan lands, so subsequent work is reviewable as real diffs. Pushing to a remote is your call (needs your account/repo target), not something to do unprompted.
- **Fix the flash-prop bug.** `app/Http/Middleware/HandleInertiaRequests.php::share()` currently returns only `auth` and `ziggy`. Add a `'flash' => fn () => ['success' => $request->session()->get('success'), 'error' => $request->session()->get('error')]` entry (or equivalent), matching what `resources/js/Layouts/AfyaShell.vue:16-17` already expects to read. Then fix `app/Http/Controllers/Clinical/BreakGlassController.php`'s `store()` method, which calls `->with('flash.success', ...)` — change to `->with('success', ...)` to match every other controller in the app. This one middleware fix makes every existing and about-to-be-built controller's success/error messaging actually work for the first time.
- **2FA: add the missing nav link, delete the dead duplicate page.** `resources/js/Pages/Profile/Edit.vue` already has a fully working inline "Two-Factor Auth" tab (sidebar item, tab button with a live-status dot, `TwoFactorAuthenticationForm.vue` partial wired to real `mfaEnabled`/`qrCodeUrl`/`recoveryCodes` props from `ProfileController::edit`) — it's just never linked to. Add a "Two-Factor Auth" item to `resources/js/Components/Workspace/AfyaHeader.vue`'s user-menu dropdown (lines ~208-235, between the existing "User Settings" and "Sign Out" links), pointing at `route('profile.edit')`. Separately, `resources/js/Pages/Profile/TwoFactorAuthentication.vue` + `TwoFactorAuthenticationController::show()` + the `two-factor.show` route (`routes/auth.php:70-71`) are a fully redundant, never-linked duplicate of the same feature — delete the Vue page and the `show()` method + route line. Leave `store`/`confirm`/`destroy`/`regenerateRecoveryCodes` on the controller untouched; `TwoFactorAuthenticationForm.vue` posts to those and they stay live.
- **Strip NIDA from the patient-registration draft autosave.** `resources/js/Pages/Domains/Patient/Register.vue`'s `saveDraftToSession()` currently persists the full form — including the 20-digit NIDA national ID — to `sessionStorage` in plaintext on every keystroke. Remove `nida` from the `payload` object (and from the `watch()` trigger list) so the autosave keeps its "don't lose your work on a power cut" value for name/DOB/contact/address fields without ever writing the one field the backend treats as sensitive enough to encrypt at rest.
- **Break-glass: share state + add a revoke banner.** Add a `breakGlass` entry to `HandleInertiaRequests::share()` (e.g. `fn () => $request->session()->has('break_glass.patient_id') ? ['patientId' => ..., 'expiresAt' => ...] : null`). Add a banner to `resources/js/Layouts/AfyaShell.vue` right after the existing flash-message block (lines ~37-56, same visual pattern) — `v-if="page.props.breakGlass"`, showing a live countdown to `expiresAt` and a button that does `router.delete(route('clinical.break-glass.destroy'))`. This also fixes "no way to end an override early" as a side effect of finally surfacing the state at all.
- **Field-level error handling on the two silent-failure workspaces.** `resources/js/Pages/Workspace/InventoryWorkspace.vue` (6 `useForm` instances: `requisitionForm`, `newItemForm`, `transferForm`, `poForm`, `grnForm`, `confirmTransferForm`) and `resources/js/Pages/Workspace/AccessControlWorkspace.vue` (`assignRoleForm`, `rolePermissionsForm`) currently have zero `form.errors`/`InputError` usage anywhere. Add `resources/js/Components/InputError.vue` (already the established pattern — see `BreakGlassModal.vue:112,135`) under each field in both files' modals.
- **Delete two dead/orphaned routes.** `routes/web.php`: remove `lab-orders.collect` / `lab-orders.results` (superseded by `laboratory.items.collect`/`.results`, confirmed zero frontend callers) and `access-control.facilities.assign` (points at a controller method, `assignFacility`, that doesn't exist on `AccessControlWorkspaceController` at all — confirmed by full read — would throw `BadMethodCallException` if ever hit).
- **Tooling scaffolding (parallel, zero dependency on anything above).** Add ESLint + Prettier (flat config, Vue 3 + Vite-aware) and Vitest (`vite.config.js` already has the Vite foundation Vitest needs — add a `vitest.config.js` or extend the existing config, plus `@vue/test-utils`). Config only in this phase — actual tests come in Phase F3 once there's new UI to test.

## Phase F1 — Backend relations + new clinical module UI

The largest phase. Four ordered sub-parts — later parts genuinely depend on earlier ones (Profile.vue's read-only rollup tabs display data the ClinicalWorkspace tabs create; Radiology's workspace has no page to extend at all, so it's correctly last).

### F1.0 — Backend prerequisite

The 8 new backend modules were built with correct `BelongsTo` relations pointing back to `Encounter`/`Patient`, but the inverse `HasMany` relations were never added to those two parent models — confirmed by reading both files in full. Add to `app/Domains/Clinical/Models/Encounter.php`: `consents()`, `referrals()`, `immunizations()`, `ancEncounters()`, `partographEntries()`, `radiologyOrders()` (mirror the existing `labOrders()`/`procedureOrders()` style). Add to `app/Domains/Patient/Models/Patient.php`: `problems()`, `medicationReconciliations()`, `referrals()`, `radiologyOrders()` (these last two go straight to Patient via each model's own `patient_id` FK, for the Profile.vue rollup tabs in F1.2). Then thread the new relations into the two controllers that load encounter/patient data for these pages: `app/Domains/Clinical/Http/Controllers/EncounterController.php` (the `with([...])` eager-load list is duplicated verbatim between `index()` and `workspace()` — add to both) and `app/Domains/Patient/Http/Controllers/PatientController.php::show()`.

### F1.1 — Five new ClinicalWorkspace chart tabs + Imaging order tab (six total)

`resources/js/Pages/Workspace/ClinicalWorkspace.vue`'s existing charting tab-strip (`chartingTab` ref, tab buttons ~lines 1178-1236, panels ~1240-1276) is the established slot — vitals/notes/prescriptions/labs/procedures already work exactly this way, each panel importing a plain SFC. Build six new components following `VitalsForm.vue`'s exact shape (`useForm()` with fields matching the controller's validated fields 1:1, `form.post(route('x.store', encounterId), {preserveScroll:true, onSuccess, onError})`, local success/error banners — keep this local-banner pattern rather than the shared `flash` prop, since per-form inline feedback is better UX regardless of the F0 flash fix, and a history table below), in this order (simplest/most isolated first, ANC→Partograph last since `storePartograph` accepts an optional `anc_encounter_id` link back to the ANC visit):

1. `resources/js/Pages/Domains/Clinical/ConsentForm.vue` — fields from `ClinicalCareExtensionsController::storeConsent` validation (consent_type select, procedure_title, explanation_of_risks, alternative_treatments, signatory_type, signatory_name, witness_name, interpreter_used, language_used) → posts `clinical.consent.store`.
2. `resources/js/Pages/Domains/Clinical/ImmunizationForm.vue` — fields from `storeImmunization` (vaccine_code, vaccine_name, dose_number, batch_number, expiration_date, administration_site, route select, adverse_reaction_notes, next_due_date) → `clinical.immunization.store`.
3. `resources/js/Pages/Domains/Clinical/ReferralForm.vue` — fields from `storeReferral` (to_facility_id/external_facility_name, urgency select, specialty_required, clinical_summary, investigations_performed, treatments_given, reason_for_referral, transport_mode) → `clinical.referral.store`. History table shows `referral_number`/`status` read-only — no accept/dispatch/complete transition UI, since no backend action exists for those transitions (`ClinicalReferral`'s migration models a status lifecycle but only `CreateReferralAction` exists — don't build UI ahead of the backend that would support it).
4. `resources/js/Pages/Domains/Clinical/AncVisitForm.vue` — fields from `storeAncVisit` (gravida, para, last_menstrual_period, estimated_date_of_delivery, gestational_age_weeks, fundal_height_cm, fetal_presentation select, fetal_heart_rate_bpm, fetal_movement select, urinary_protein, iptp_malaria_dose, iron_folate_given, high_risk_flag + high_risk_reason) → `clinical.anc.store`.
5. `resources/js/Pages/Domains/Clinical/PartographForm.vue` — fields from `storePartograph` (cervical_dilation_cm, fetal_heart_rate_bpm, liquor_status select, fetal_head_descent, uterine_contractions_per_10min, contraction_duration_seconds, maternal_systolic_bp/diastolic_bp/pulse_bpm, alert_line_crossed/action_line_crossed, midwife_remarks) → `clinical.partograph.store`. Given entries happen in rapid succession during active labor, a denser inline-row layout (vs. `VitalsForm`'s block grid) is worth considering — a UX call for whoever implements, not a blocker.
6. `resources/js/Pages/Domains/Clinical/ImagingOrderForm.vue` — fields from `RadiologyWorkspaceController::order` (modality select: X-Ray/Ultrasound/CT Scan/MRI/Echo, procedure_name, body_site, clinical_indication, priority) → `radiology.orders.store`. This is the *ordering* half of radiology only — reporting (sign/amend) is a separate radiologist-side worklist, built in F1.3, not a 7th tab here.

Wire all six into `ClinicalWorkspace.vue`: six imports, six tab-strip buttons (copy the existing "Procedures & Surgery" button's markup/badge-count pattern), six `v-else-if="chartingTab === '...'"` panels reading `activeEncounter?.x || []` off the F1.0 relations. ANC/Partograph are only clinically relevant for maternity encounters — consider gating their tab visibility on `encounter.encounter_type` rather than always showing all 11 tabs, but that's a UX refinement, not required for correctness.

### F1.2 — Patient-scoped tabs in Profile.vue

`resources/js/Pages/Domains/Patient/Profile.vue` already has two ready-made stub tabs — `imaging` (lines ~706-711) and `referrals` (~727-732) — currently static empty-state placeholders. Replace both with real tables sourced from the F1.0 `patient.radiologyOrders`/`patient.referrals` relations, following the existing `diagnoses` tab's table pattern (lines ~566-596: `Table`/`TableRow`/`TableCell`, `AfyaStatusBadge` for status, empty-state row). No "create" button on either — creation happens in ClinicalWorkspace (F1.1); these are read-only rollups.

Add two new tabs that don't exist yet:
- **Problem List** — new `problems` computed (`props.patient.problems || []`) and a new sidebar/tab entry, distinct from the existing `diagnoses` tab (which is genuinely different data — encounter-level ICD codes, not the longitudinal active/resolved `PatientProblem` list with severity/clinical-status). Needs a record form (icd10_code, problem_name, encounter_id, status, clinical_status, severity, onset_date, notes → `clinical.problems.store`) plus a resolve action per active row (→ `clinical.problems.resolve`), since `ManageProblemListAction` supports both.
- **Medication Reconciliation** — new `medicationReconciliations` computed and a new tab (the existing `medications` tab only lists `prescriptions`; reconciliation is a distinct, stage-based workflow, cleaner as its own tab than folded in). Build last in this sub-phase — it's the structurally most complex of the F1/F2 forms, the only one with a nested repeatable array field: `stage` select (Admission/Transfer/Discharge), then a repeatable row group for `medications[]` (medication_name, dosage, frequency, route, action_taken select: Continue/Discontinue/Substitute/ModifyDose/Hold, clinical_rationale, substitute_medication_name, new_dosage_instructions) → `pharmacy.reconciliation.store`.

### F1.3 — Radiology workspace (new page, built last)

`RadiologyWorkspaceController`'s own docblock states no `index()`/listing page exists "on purpose... a workspace listing UI is frontend scope to add alongside a Vue page later" — this is that page. Add `index(): Response` to the controller (eager-loading `order.patient`, `order.encounter`, `order.studies`, `order.reports`, split into pending/awaiting-report/signed buckets), a `GET /radiology` route, and `resources/js/Pages/Workspace/RadiologyWorkspace.vue` following `LaboratoryWorkspace.vue`'s established shape almost exactly: `activeSection` ref driving sidebar-section switching (`pending`/`reporting`/`signed`, mirroring Lab's phlebotomy/testing/completed), a context-inspector right panel showing the selected order's detail, and two modals — Sign Report (findings/impression/recommendations/is_critical_finding → `radiology.report.sign`) and Amend Report (same fields + required amendment_reason, min 10 chars → `radiology.report.amend`), directly mirroring `SOAPNote.vue`'s existing sign/amend modal pair. No order-creation UI here — that's F1.1's Imaging tab, on the encounter side.

## Phase F2 — Remaining orphaned-route UI

Smaller, independent fixes to existing pages (no new pages needed):

- **Appointment creation.** `resources/js/Pages/Domains/Scheduling/Calendar.vue` has a dead unused `Plus` icon import — the clearest signal a "New Appointment" button was intended but never built. `AppointmentController::index` (`app/Domains/Scheduling/Http/Controllers/AppointmentController.php`) needs to additionally load `patients`/`facilities`/`providers`/`departments` for a create form to have anything to select from. Add the button + a create modal (`patient_id`, `facility_id`, `department_id`, `provider_id`, `scheduled_time`, `duration_minutes`, `appointment_type`, `notes` → `appointments.store`).
- **DDA log + stocktake "New" actions.** `resources/js/Pages/Workspace/InventoryWorkspace.vue`'s DDA section (~lines 1331-1384) and stocktake section (~1438-1491) are both confirmed read-only tables with zero creation button — every other section in the same `#actions` template block (~582-660) has one, these two don't. Add matching "New DDA Entry" / "New Stocktake Session" buttons + forms, posting to `inventory.dda-logs.store` / `inventory.stocktake.store`.
- **Billing Issue/Adjust actions.** `resources/js/Pages/Workspace/BillingWorkspace.vue`'s invoice inspector panel (~lines 545-620, where "Charge Items" already lives) is the right home for two new actions: "Issue Invoice" (locks for checkout, → `billing.invoices.issue`) and "Adjust (Credit/Debit Note)" (→ `billing.invoices.adjust`, fields: type Credit/Debit, amount, reason), following the exact pattern already used for the adjacent pay/refund buttons.
- **Explicitly out of scope for this pass:** `billing.generate` (no encounter-detail page exists anywhere to host a "Generate Invoice" trigger — this needs a product decision on where that belongs, not a bug fix) and `pharmacy.inventory` (on inspection, this renders the identical already-linked `PharmacyQueue.vue` page just defaulting to a different in-page tab that's one click away — not a real gap, safe to leave as-is or add a one-line nav shortcut later if it comes up again).

## Phase F3 — Tests for what F1/F2 just built + i18n infrastructure

- **Vitest starter suite**, using the F0 scaffolding: cover the highest-value paths first — the 2FA challenge flow (`TwoFactorChallenge.vue`), the break-glass modal + new revoke banner, one representative new F1.1 clinical form end-to-end (e.g. `ConsentForm.vue`), and `RadiologyWorkspace.vue`'s sign/amend modals. This isn't "achieve broad coverage across 94 files" — it's establishing the pattern and covering the security/clinical-safety-critical paths, the same incremental way the backend's Pest suite was built up across this whole engagement.
- **i18n infrastructure.** Install and configure `vue-i18n`, extract existing hardcoded strings into an English locale file as the baseline. Deliberately *not* translating to Swahili in this pass — that's a content-authoring task that deserves native-speaker review, not something to rush through as part of a bug-fix pass. Doing extraction after F1 (rather than before) avoids pulling strings out of components that don't exist yet.

---

## Phase F4 — Accessibility

Target the shared Afya component library first — `AfyaInput.vue`, `Modal.vue`, `Button.vue`, and the `ui/Table*.vue` primitives — rather than a manual per-page sweep of all 94 files, since fixing ARIA attributes, focus management, and keyboard handling once at the primitive level propagates to every page that already uses them. Where possible, land this *before* F1's new components are written, so they inherit correct primitives from day one instead of needing a second retrofit pass immediately after shipping.
